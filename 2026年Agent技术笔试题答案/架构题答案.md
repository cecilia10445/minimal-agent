# 2026 年 Agent 技术笔试——架构设计题

## 背景说明

在 Vibe Coding 部分，我实现了一个最小可用 Agent Runtime：模型负责判断直接回答或调用工具，Runtime 负责执行工具、回填结果、管理 Session 和控制循环。项目还实现了 SQLite 持久化、基础 Context 压缩、异常处理和 Trace。这个过程让我实际接触到了 Agent 系统中几个最核心的问题：上下文会变长、记忆会过期、长任务会偏离目标、异步事件会争抢 Session、不同模型的工具协议也存在差异。

下面从这些实践中引出问题，再讨论面向真实 Agent 产品的通用解决方案。

---

## 模块一：2.一个 session 连续聊了 200 轮，context 快爆了。你会怎么做压缩？如何确保压缩后的对话仍然流畅？

在最小 Agent 中，我采用了比较基础的压缩方式：历史长度达到阈值后，以完整用户轮次为边界压缩较早消息，保留最近几轮原始对话，并保证工具调用和工具结果不会被拆散。 这个方案能够满足基础题目要求，但 200 轮会话带来的问题远远超过 Token 超限。

长会话中至少存在四类信息。第一类是最近几轮的原始表达，它决定“继续刚才那个方案”“把第二点改一下”这类追问能否被正确理解。第二类是长期有效的信息，例如用户偏好、项目约束和已经确认的决定。第三类是当前任务状态，例如执行到哪一步、还有什么没有完成。第四类是文件列表、待办、异步任务进度等动态数据，这些内容可能已经发生变化。

这几类信息的更新频率和召回方式不同。把它们全部写进同一份滚动摘要，经过多轮压缩后容易出现事实漂移；只保留最近消息，又会丢掉几十轮以前的重要决定；每次检索所有历史，则会增加延迟并产生大量无关召回。

目前比较合理的方向是分层管理 Context。OpenHands 的 Condenser 会在历史超过阈值时选择保留部分事件，并将被遗忘的事件压缩成摘要；它同时保留原始事件日志，供后续恢复和重新构建上下文。近期 Coding Agent 也越来越重视 Context Compaction，通过压缩旧历史延长长任务的稳定执行时间。

我的方案会将一次模型调用的 Context 分为四层。

最靠近模型的是最近原始窗口，保留最近四到八个完整对话轮次，其中包括用户消息、模型回复、Tool Call 和 Tool Result。它负责维持局部语言连贯性。

第二层是当前工作状态，保存目标、关键约束、最新决定、已完成事项和下一步。这部分由 Runtime 维护，事实发生修正时直接更新当前值。例如截止日期从周五改到周六，后续 Context 中重点保留周六，并留下简短的修改来源。

第三层是会话摘要，用于保存较早阶段发生过的重要过程。摘要可以帮助模型理解事情的发展，但优先级低于当前工作状态和最新消息。

第四层是远期历史检索。原始历史继续存储，当前问题涉及早期内容时，再按语义相关性、关键词、时间和重要程度召回少量片段。远期检索采用按需触发，可以控制成本和噪声。

动态信息通过工具获取最新结果。历史中的文件列表可以帮助模型理解过去做过什么，当前文件是否存在仍需重新读取目录。Todo、部署状态、任务进度也遵循相同原则。

压缩触发可以结合 Token 使用率和模型上下文上限。例如达到预算的 70% 时开始后台整理，达到 85% 时强制压缩。压缩过程需要保留完整交互边界，并为 System Prompt、当前任务状态和下一轮工具结果预留空间。

摘要质量还需要持续校验。系统可以为重要事实设置固定探针，例如项目目标、最新截止时间、禁止事项和当前阻塞。探针召回失败时，从原始历史重新构建摘要。这样能够控制多次摘要叠加造成的误差。

最终方案可以概括为：最近原文维持表达连贯，当前状态保证事实准确，会话摘要保存过程，远期检索负责早期回忆，动态信息通过工具获取。四层信息各自承担一种职责，200 轮对话仍然可以保持较小且稳定的活动 Context。

## 模块二：1.和聊天 Agent 熟悉半个月后，用户问了一个以前问过的问题。Agent 如何做 memory 召回更合理？

Session 历史解决的是“继续当前窗口聊天”，长期 Memory 解决的是“跨越多个窗口和较长时间后，仍然理解这个用户”。我实现的最小 Agent 已经可以恢复同一 Session 的消息和摘要，但长期 Memory 还需要独立的写入、检索、更新和删除机制。

长期 Memory 的第一步是判断当前问题是否需要历史信息。用户询问普通技术知识时，历史召回带来的帮助有限；用户提到“上次”“按照我的偏好”“之前决定的方向”时，过去信息会直接影响答案。系统可以使用规则和轻量模型完成这次判断，减少每轮无条件检索带来的延迟。

需要召回时，检索范围先限定在当前用户，再根据具体场景缩小到某个项目或主题。用户长期偏好可以跨 Session 使用，项目截止日期只在对应项目中生效，某次临时讨论则保持在原会话范围内。

候选 Memory 的排序需要结合语义相关性、关键词、时间、重要程度和使用频率。语义检索适合发现表达不同但含义接近的内容；关键词适合姓名、项目名、日期和数字；时间与重要度可以防止一条很久以前的普通聊天压过最近的明确决定。

事实冲突需要专门处理。用户的偏好和计划会变化，系统需要保留修改关系和时间信息。例如用户半个月前希望去深圳，后来明确改成只考虑上海，召回阶段应优先使用最新结论。多条记录存在矛盾且缺乏明确修正时，回答中可以主动确认当前偏好。

Memory 进入 Context 时，应当保持数量精简，并说明这是过去确认过的信息。模型还需要遵循一个优先级：当前用户输入最高，其次是最新工具结果，然后是长期 Memory。这样可以减少旧信息覆盖当前意图的情况。

回答结束后，再判断这次对话是否值得写入 Memory。稳定偏好、长期目标、明确约束、重要决策和用户主动要求记住的内容具有较高价值。一次性情绪、临时状态和敏感信息需要更严格的条件。用户还应拥有查看、纠正、删除和关闭 Memory 的能力。

从产品实践来看，ChatGPT 将 Saved Memories 和 Chat History Reference 分开：前者用于较稳定、希望长期保留的信息，后者从过去聊天中动态引用有用内容，并且不会保存每个细节。 Anthropic 的 Memory Tool 则采用客户端存储和 Just-in-Time Retrieval，Agent 将经验保存到持久目录，需要时再读取，活动 Context 可以继续聚焦当前任务。

这些实践体现了两个趋势。第一，长期 Memory 开始与完整聊天历史分离；第二，用户控制、时间有效性和按需召回逐渐成为核心能力。

我的完整方案是：先判断问题是否依赖过去，再按用户和项目范围检索候选 Memory，通过相关性、时间和重要度排序，解决新旧事实冲突，只选取少量内容放入 Context。回答完成后，再根据价值和敏感程度决定是否更新 Memory，并提供用户可见的管理入口。

## 模块三：1.对于长程任务，大模型执行一段时间可能会忘掉目标，你知道哪些解决方案，有什么优缺？

实现最小 Agent 时，我使用 `max_steps` 防止工具循环失控，同时通过 Todo 和 Trace 记录简单任务与执行过程。它们能够解释“执行了什么”，却无法完整表达“最终目标是什么、目前处于哪个阶段、距离验收还缺什么”。

长程任务中的目标漂移通常来自三个方面。首先，原始目标逐渐被大量工具结果和报错信息淹没。其次，模型专注于解决眼前问题，局部优化可能偏离整体要求。最后，多次重新规划会改变任务路径，如果验收条件没有独立保存，模型容易把当前计划当成最终目标。

常见方案包括完整规划、Todo、周期性 Reflection、任务图、状态机、检查点和外部验证。完整规划适合步骤明确的任务，环境发生变化时需要重新调整。Todo 可以帮助模型记住下一步，但它缺乏依赖关系和完成证据。Reflection 有助于发现方向偏移，使用过于频繁会增加成本并形成反复分析。严格状态机适合业务流程，开放型研究任务需要保留更多探索空间。

长程任务更适合采用分层控制。

第一层保存任务目标、关键约束和验收标准。这部分由 Runtime 管理，每轮都可以简短注入。目标发生变化时，需要通过明确的用户指令或审批过程更新。

第二层保存阶段计划。任务开始时只规划几个高层阶段，例如分析、实现、验证和交付。进入某个阶段后，再生成局部步骤。这样能够兼顾方向稳定和执行灵活性。

第三层保存进度账本。每次动作结束后，记录已经完成的工作、产生的证据、当前阻塞和下一步。模型下一次推理时读取精简后的账本，无需重新理解全部工具历史。

第四层加入检查点和验证器。代码 Agent 完成修改后运行测试、静态检查和构建；数据 Agent 校验数据范围与统计口径；高风险操作等待人工审批。任务是否完成由验收证据决定，模型负责解释这些证据。

第五层是重新规划。出现连续失败、环境变化或阶段目标完成时，系统重新读取原始目标、当前进度和失败记录，生成后续计划。重新规划需要保留已经确认的成果，避免重复工作。

Codex 的公开产品设计体现了这种 Harness 思路：任务在独立沙箱中执行，可以读取和修改代码、运行测试与检查，并根据结果持续迭代。后续 Codex 模型还强化了长程工作中的 Context Compaction，以支持大型重构、迁移和多次失败后的持续执行。

市场上的 Coding Agent 已经逐渐从“模型持续聊天”发展为“模型加工作区、任务状态、测试环境、日志和恢复机制”。Harness 为模型提供稳定目标和外部证据，模型负责选择下一步行动。

我的最终方案由固定目标、阶段计划、进度账本、检查点验证和条件式重新规划组成。目标决定方向，计划组织步骤，进度记录事实，验证器判断结果，重新规划处理变化。长任务由此可以跨越多轮模型调用、工具失败和进程重启继续执行。

## 模块四：2.如果 session state 为 busy，此时用户又发来新消息，或者异步工具完成事件也到达，runtime 应该如何处理？

最小 Agent 的工具执行采用同步流程：模型请求工具，Runtime 等待工具返回，再把结果交给模型。 计算器和文档读取通常可以快速完成，视频生成、大型代码扫描、数据分析和人工审批可能持续几分钟甚至更久。这类工具需要从同步请求中拆出，交给后台 Worker 处理。

异步工具接入后，用户消息和工具完成结果都可能修改同一个 Session。核心问题是并发顺序和状态一致性。

我会为每个 Session 设置一个串行事件队列。用户消息、工具完成、工具失败、取消请求和超时事件都先进入队列，由该 Session 的单一执行者按顺序处理。这样可以避免两个线程同时读取旧状态并覆盖彼此。

假设用户发送消息 A，Runtime 创建 Run A，并启动一个异步工具。系统保存当前进度，向用户返回“任务已受理”，后台 Worker继续执行。此时用户又发送消息 B，Runtime 先识别 B 与 Run A 的关系。

普通新问题可以排队，等待 Run A 结束后处理。补充信息可以附加到 Run A，在下一次模型调用时生效。取消、暂停和改变目标属于控制指令，需要更新 Run A 的状态，并决定是否向工具发送取消信号。

工具 A 完成后，结果进入同一个事件队列。Runtime 检查结果对应的 Run、工具调用和当前版本。Run A 仍然有效时，将结果写成 Observation 并恢复模型执行。Run A 已经取消或被替换时，结果保留为历史产物，同时标记为过期，避免旧任务重新启动。

重复回调通过幂等控制解决。同一次工具执行无论返回几次，Session 只消费一次。状态更新可以增加版本号，Worker 提交结果时检查自己读取的版本是否仍然有效。超时后到达的结果遵循同样规则。

用户体验层面需要显示任务状态，包括已排队、执行中、等待外部结果、完成、失败和取消。长工具可以直接上报进度，进度变化无需每次调用模型。用户离开当前页面后，可以通过消息中心或应用通知获得结果。

OpenHands 当前采用事件驱动思路：Agent 的每个 Step 相对独立，从事件历史读取状态并写入新的 Action 或 Observation；事件日志采用追加式存储，可以用于恢复、观察和服务集成。工具级错误进入 Observation 后，Agent仍可以继续处理；会话级错误则结束当前运行。

完整事件系统适合长任务和分布式 Agent，中小型 Runtime 可以控制复杂度。Session 串行队列、独立 Run 状态、异步工具记录、幂等处理和版本检查已经能够覆盖主要问题。

我的最终处理策略是：每个 Session 保持单写入者，所有外部输入统一排队；普通消息按顺序执行，控制指令可以中断当前 Run；工具结果写回前验证所属 Run 和状态版本；重复或迟到结果安全丢弃或归档。这个方案能够同时处理 busy Session、新消息和异步完成事件，并为暂停、取消和崩溃恢复留下扩展空间。

## 模块五：1.Claude Code 的工具输出方式和国内 GLM / 豆包等 OpenAI-compatible function calling 有什么不同？他们各自这样设计的优缺点是什么？

这道题包含模型协议和 Agent 产品两个层次。

Anthropic Messages API 使用内容块组织回复。Claude 可以在同一条 assistant 消息中按顺序输出文本块和 `tool_use` 块。应用执行客户端工具后，将 `tool_result` 内容块放入下一条 user 消息，并通过 ID 与原工具请求关联。Anthropic 还区分客户端工具和服务端工具：客户端工具由应用执行，Web Search、Code Execution 等服务端工具可以由 Anthropic 基础设施完成。

OpenAI-compatible Chat Completions 常见形式是 assistant 消息返回 `tool_calls`，应用执行函数后，再通过独立的 `tool` 角色消息和 `tool_call_id` 回填结果。OpenAI Function Calling 允许模型根据函数描述和参数约束生成调用参数，Structured Outputs 还可以通过严格模式强化参数与 Schema 的一致性。

火山方舟等国内平台提供 OpenAI SDK 兼容接入，通过修改 Base URL、模型和 API Key 即可迁移现有客户端；其 Responses API 也支持 Function Calling、内置工具、知识库检索和 MCP。 GLM、豆包和其他模型即使使用相似协议，在并行工具调用、参数准确率、严格 Schema、流式增量和错误返回方面仍可能存在差异，因此兼容性需要通过真实测试确认。

Anthropic 内容块的优势在于表达顺序清晰。文本、工具请求和其他内容类型可以组合在同一条消息中，流式客户端能够观察模型输出如何逐步进入工具调用。协议还便于扩展 Bash、Text Editor、Memory、Computer Use 等训练过的标准工具。客户端需要处理多种内容块、严格的排列规则和工具结果关联，实现复杂度相对较高。

OpenAI-compatible Function Calling 的优势是接入范围广，SDK 和中间件生态成熟。许多模型服务可以复用同一套客户端，适合建立多模型基础接入层。各家扩展字段和具体行为存在差异，统一接入后仍需保留 Provider 能力检测。

Claude Code 处于更高一层。它围绕模型协议增加终端、文件系统、权限确认、Session 恢复、Hooks、流式事件和工作区管理。用户看到的工具过程已经由 Agent Harness 组织。Codex 同样通过独立沙箱、仓库环境、测试和任务状态，将模型调用扩展成完整的软件工程执行系统。

行业中的工具架构还在继续发展。Anthropic开始提供版本化的标准工具、Tool Search、Memory 和 MCP Connector；OpenAI也在推进 Programmatic Tool Calling，让模型在受控运行环境中完成多次工具调用、过滤和聚合，减少模型与客户端之间的往返次数。 这说明工具系统正在从“模型返回一次函数名”发展为完整的工具发现、执行、审批、组合和结果管理。

设计多模型 Agent Runtime 时，我会设置独立的 Provider Adapter。Anthropic 内容块、OpenAI-compatible Tool Call 和厂商扩展格式先在适配层中解析，核心 Runtime 接收到统一的文本结果、工具请求和执行状态。统一层只覆盖公共语义，Prompt Cache、服务端工具、Tool Search 和流式内容块等高级能力通过可选能力继续保留。

适配层还需要维护能力矩阵，并使用同一批测试验证直接回答、单工具、多工具、参数错误、流式中断和工具失败。接口兼容只能降低接入成本，真实行为仍要通过评测确认。

最终方案可以概括为：模型协议由 Provider Adapter 负责，工具执行、Session、权限和恢复由 Agent Harness 负责；公共语义在 Runtime 内统一，厂商特有能力通过扩展接口使用。这样既能支持 GLM、豆包、Qwen 等 OpenAI-compatible 服务，也能接入 Anthropic 内容块协议，并保留各平台有价值的高级功能。

## 总结

实现最小 Agent 之后，我对 Agent 架构的理解逐渐形成了一条完整链路。

Context 解决模型本轮看到什么；Memory 解决过去哪些信息值得重新出现；Task State 解决长任务如何保持方向；Session Runtime 解决异步、并发和恢复；Provider Adapter 解决多模型协议差异；Agent Harness 则把模型、工具、工作区、权限、日志和验证组织成一个可持续执行的系统。

Vibe Coding 部分验证了最小同步闭环。架构设计部分关注闭环规模扩大后出现的问题，以及当前主流 Agent 产品采用的解决思路。最终目标是让模型专注于判断和生成，让 Runtime 负责状态、执行和可靠性。
