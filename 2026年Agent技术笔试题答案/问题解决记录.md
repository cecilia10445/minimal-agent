# 问题解决记录
## 1. 说明

本记录整理项目开发过程中实际遇到的主要问题，以及本人如何结合 AI 建议作出技术判断。

每条记录按照以下结构：

```
问题
Prompt
AI 建议
我的判断
实际结果
```

重点记录需求拆解、架构决策、人工测试和问题收口。

## 2. 不使用 Agent 框架时如何组织核心流程

### 问题

题目要求不能依赖 LangGraph、OpenHands、OpenClaw 等 Agent 框架控制主流程，但又要求实现 LLM 决策、工具调用、Observation 回填和多步循环。

如果将所有逻辑写在一个函数中，后续很难测试，也无法证明核心 Runtime 是自行实现的。

### Prompt

提示词：第二轮次

### AI 建议

将项目拆成：

- `AgentRuntime`
    
- `LLMClient`
    
- `ToolRegistry`
    
- `SessionStore`
    
- `TraceStep`
    

其中：

- LLMClient 只负责一次模型调用；
    
- ToolRegistry 负责工具查找和执行；
    
- AgentRuntime 负责整个循环；
    
- ScriptedLLMClient 用于确定性测试。
    

### 我的判断

我接受分层方案，但明确要求：

- 不能让 OpenAI SDK 自动完成工具循环；
    
- 不能在 Qwen Client 中执行工具；
    
- 所有工具调用必须回到自研 AgentRuntime；
    
- Agent Loop 必须能在源码中清晰展示；
    
- 适配器可以替换，Runtime 不能绑定具体模型厂商。
    

### 实际结果

形成清晰的核心循环，并通过直接回答、单工具、多工具、工具异常和最大步骤测试。

## 3. 工具如何访问 Session 状态而不暴露 session_id

### 问题

Todo 工具需要访问当前 Session，但如果将 user_id 和 session_id 放进工具 Schema，模型就可能传入或修改其他 Session ID，破坏隔离边界。

### Prompt

提示词：第一轮次

### AI 建议

由 Runtime 创建：

```
ToolContext(user_id, session_id, store)
```

工具执行时由 Runtime 注入，LLM 只生成业务参数。

### 我的判断

接受 ToolContext 注入方式。

我进一步确认：

- Todo 属于当前 Session；
    
- calculator 无状态；
    
- search 和本地知识文档是全局只读资源；
    
- LLM 永远不能决定当前 user_id 和 session_id；
    
- Session 隔离属于 Runtime 责任，不属于 Prompt 约束。
    

### 实际结果

Todo 工具能够在同一 Session 内共享状态，不同 Session 互不影响，模型无法通过参数越权访问其他 Session。

---

## 4. 如何接入真实 Qwen 而不破坏自研 Runtime

### 问题

题目要求使用真实 LLM API，但接入 SDK 后容易将工具循环交给 SDK 或在模型适配器中重复实现 Runtime。

### Prompt

提示词：第三轮次

### AI 建议

实现 `OpenAICompatibleLLMClient`：

```
SDK response
→ 解析 content
→ 解析 tool_calls
→ 转成内部 LLMResponse
```

Client 每次只调用模型一次。

### 我的判断

我要求保持严格边界：

- Qwen Client 不执行工具；
    
- 不在 Client 中写 `while tool_calls`；
    
- 工具由 AgentRuntime 执行；
    
- Base URL、模型和 Key 通过环境变量配置；
    
- 普通测试不调用真实 API；
    
- 真实 API 测试显式开启。
    

### 实际结果

真实 qwen3.6-plus 成功完成普通对话、calculator、search、Todo 和多工具调用，核心 Runtime 未依赖厂商 SDK 的自动 Loop。

## 5. Trace 为什么在多轮后看起来顺序错误

### 问题

真实 CLI 中，多次对话后输出：

```
Step 1
Step 1
Step 2
Step 1
Step 2
```

实际执行没有错误，但普通回答区域打印了 Session 累计 Trace，导致不同 run 混合。

### Prompt

提示词：第四轮次

### AI 建议

- 每次 run 记录 trace 起始索引；
    
- AgentResult 只返回本次新增 Trace；
    
- TraceStep 增加 run_id；
    
- `/trace` 再按 run_id 展示累计记录。
    

### 我的判断

我接受“本次 Trace”和“Session 累计 Trace”分离，而不是将 Step 编号改成全局递增。

原因是 Step 语义应当表示单次 Agent Loop 的执行步数，每次 run 从 1 开始更清晰。

### 实际结果

普通回答只显示当前请求的 Trace，`/trace` 可以查看完整 Session 执行记录。

## 6. 内存 Session 为什么无法跨终端恢复

### 问题

多个终端看起来可以隔离，但关闭终端后重新进入相同 Session，之前的 Todo 和对话全部消失。

### Prompt

提示词：第六轮次

### AI 建议

增加 SQLiteSessionStore，以：

```
(user_id, session_id)
```

作为复合主键，将 messages、summary、todos 和 traces 序列化为 JSON。

### 我的判断

我确认原来的隔离只是进程内字典隔离，不是真正的跨进程恢复。

我选择 SQLite，而不是 Redis 或 MySQL，原因是：

- 笔试题目要求最小可用；
    
- SQLite 无需额外服务；
    
- 可以真实证明关闭 CLI 后恢复；
    
- 足以展示逻辑用户和 Session 隔离。
    

我没有增加密码、注册和 JWT，因为题目没有要求身份认证。README 中只将 user_id 描述为逻辑隔离键。

### 实际结果

相同 user_id/session_id 可以跨进程恢复；同一用户不同 Session 和不同用户相同 session_id 均保持隔离。

## 7. Context 过长时为什么不能直接截断前半部分

### 问题

如果按消息数量或字符数直接删除旧消息，可能留下：

```
assistant tool_call
```

却删除对应：

```
tool result
```

或者留下孤立 Tool Result，导致模型消息结构非法。

### Prompt

提示词：第五轮次

### AI 建议

以完整 user turn 为压缩边界，保留最近 N 个用户轮次，将更早消息转换为 Session Summary。

### 我的判断

我接受完整轮次压缩，并确定 Context 只包含：

- 主 System Prompt；
    
- Session Summary；
    
- 最近完整原始消息；
    
- 当前 Tool Call 与 Tool Result。
    

我明确排除：

- 全部 Trace；
    
- 完整隐藏思维链；
    
- API Key；
    
- SQLite 元数据；
    
- Todo 全量副本。
    

Todo 等动态状态需要时重新调用工具，以工具结果作为当前事实来源。

### 实际结果

完成基础 Context 压缩，Tool Call 与 Tool Result 不拆分，并通过 39 个 Context 自动测试。

## 8. 零 API 压缩脚本是否属于“虚假演示”

### 问题

为了触发 Context 压缩，如果使用真实模型一直聊天，会浪费时间和额度。另一方面，如果脚本自行实现一套假压缩，也无法证明项目功能。

### Prompt

提示词：第九轮次

### AI 建议

演示脚本直接导入项目真实：

```
Session
ContextManager
ContextPolicy
```

人工构造标准消息数据，再调用正式压缩方法。

### 我的判断

我认为构造测试消息本身没有问题，关键是：

- 被测代码必须是项目真实 ContextManager；
    
- 不能在脚本中复制压缩算法；
    
- 脚本应显示压缩前后消息结构；
    
- 真实模型语义保持需要另外通过真实 API 探针验证。
    

因此我将测试拆成：

1. 确定性单元测试；
    
2. 合成历史回放；
    
3. 真实模型语义保持测试；
    
4. 已保存场景的离线回归。
    

### 实际结果

形成 Context 可视化脚本、Session 检查脚本、合成边界回放和真实长会话测试运行器。

## 9. 为什么旧 Session 能列出文档，而新 Session 不能

### 问题

旧 Session 可以回答知识库中有哪些文档，全新 Session 却只能猜测 `readme.md`。

人工检查 Trace 后发现，旧 Session 没有调用工具，只是在回忆以前读取过的文件名。

### Prompt

提示词：第七轮次

### AI 建议

区分：

```
Session Memory
→ 历史上读过什么

当前磁盘状态
→ 现在实际有哪些文件
```

增加：

- `list_docs`
    
- `search_docs`
    
- `read_docs`
    

三个独立工具。

### 我的判断

我确认这不是 Markdown 格式或重启问题，而是工具能力和 Memory 语义混淆。

我选择拆分三个工具，而不是在 `read_docs` 中增加复杂 action 参数，原因是：

- 每个工具职责更清晰；
    
- Schema 更容易被模型理解；
    
- Trace 更容易展示；
    
- 自动测试更容易覆盖。
    

### 实际结果

全新 Session 可以实时列出目录、搜索所有 Markdown 内容和读取指定文档。

## 10. 历史记忆为什么会覆盖当前文件状态

### 问题

第一次询问当前文件列表时调用了 `list_docs`。

随后在磁盘删除文件，再问“现在有哪些文档”，模型却直接沿用上一轮结果，直到用户追问“你确定吗”才重新调用工具。

### Prompt

提示词：第八轮次

### AI 建议

在 System Prompt 中增加 freshness 规则：

- “当前、现在、目前、全部、数量”等查询每次重新调用工具；
    
- 当前工具结果优先于 Session Memory；
    
- 历史 Tool Result 只表示当时状态。
    

### 我的判断

我没有选择在 AgentRuntime 中根据中文关键词强制调用 `list_docs`，因为题目要求 LLM 基于 Schema 自主决策。

我选择通过：

- 更清晰的工具 description；
    
- System Prompt 路由规则；
    
- 真实模型场景测试；
    

提升模型决策稳定性。

### 实际结果

真实 qwen 场景中，删除文件后再次询问，模型能够重新调用 `list_docs` 并返回当前列表。

## 11. 模糊文件名为什么会被历史文件名替代

### 问题

旧 Session 曾读取过 `介绍.md`。

用户输入：

```
读取 JavaScript介绍.md
```

旧 Session 中模型将参数替换成了历史里的 `介绍.md`；全新 Session 则正确返回两个候选：

- JavaScript介绍基础.md
    
- JavaScript介绍进阶.md
    

### Prompt

提示词：第八轮次

### AI 建议

增加规则：

- 用户提供的原始文件名必须忠实传递；
    
- read_docs 多候选时不得擅自选择；
    
- 应返回候选让用户确认。
    

### 我的判断

我接受 Prompt 和 Schema 层约束，不在 Runtime 中硬编码文件名匹配逻辑。

工具负责：

- 精确匹配；
    
- 自动补 `.md`；
    
- 单一模糊候选；
    
- 多候选返回列表。
    

模型负责根据工具结果继续询问用户。

### 实际结果

真实模糊文件名场景可以返回多个候选，模型不会擅自选择。

## 12. 长文档读取为什么看似成功却找不到末尾内容

### 问题

读取约 115 KB 的 Markdown 后，模型可以总结前部内容，但无法回答末尾识别码。

最初最终回答没有说明发生过截断，容易让用户误以为模型阅读了完整文档。

### Prompt

提示词：第八轮次

### AI 建议

`read_docs` 返回：

- original_chars；
    
- returned_chars；
    
- truncated。
    

当 `truncated=true` 时，System Prompt 要求模型明确披露只读取了部分内容。

`search_docs` 继续扫描完整文件，因此可以搜索截断区域后的关键词。

### 我的判断

我没有取消长度限制，因为将 100 KB 以上全文直接放入 Context 会造成不必要的 Token 消耗。

我选择：

- read_docs 限制单次返回长度；
    
- 明确披露截断；
    
- search_docs 用于定位末尾关键词；
    
- 不在本项目实现分块 RAG。
    

### 实际结果

真实 Qwen 场景能够说明文档已截断，并通过 `search_docs` 找到截断区域后的识别码。

## 13. 基础规则摘要是否足以保持长期语义

### 问题

确定性摘要可以稳定压缩消息，但只会按固定模板保存：

- 用户请求；
    
- 工具名称；
    
- 工具结果；
    
- 助手回答。
    

它不能可靠识别：

- 用户目标；
    
- 偏好；
    
- 事实修正；
    
- 旧值和新值的优先级；
    
- 未完成事项。
    

### Prompt

提示词：第十轮次 A、B

### AI 建议

先建立确定性压缩基线，再增加 Hybrid 语义摘要：

```
代码保护消息结构
→ Qwen 总结旧历史语义
→ 最近轮次保持原始消息
→ 失败时回退规则摘要
```

### 我的判断

我没有直接删除确定性摘要，而是将其保留为安全回退。

原因是：

- Tool 结构安全应由代码保证；
    
- 语义理解适合交给模型；
    
- API 超时、限流、非法 JSON 时不能影响当前用户请求；
    
- 默认模式应保持 deterministic，Hybrid 需要显式开启；
    
- 不能把动态 Todo 状态长期当成摘要事实。
    

我将语义摘要字段限制为：

- goals；
    
- confirmed facts；
    
- latest corrections；
    
- preferences；
    
- constraints；
    
- completed actions；
    
- open items；
    
- document references。
    

### 实际结果

完成 Hybrid 语义压缩和确定性回退。FakeSemanticSummarizer 测试验证成功和失败两条路径，真实评测用于对比事实召回和压缩效果。

## 14. 自动测试和真实模型测试如何分工

### 问题

ScriptedLLMClient 可以稳定验证 Runtime，但不能证明真实 Qwen 一定选择正确工具；只依赖真实模型又会导致测试不稳定、耗费额度。

### Prompt

提示词：第八轮次、第十轮次 A

### AI 建议

分层测试：

1. pytest + ScriptedLLMClient；
    
2. 工具单元测试；
    
3. 合成历史回放；
    
4. 真实 Qwen 场景运行器；
    
5. 人工 CLI 验收。
    

### 我的判断

我要求不同测试不得相互冒充：

- Fake 测试证明代码结构和异常路径；
    
- 真实 API 测试证明模型路由和语义行为；
    
- 零 API 演示证明真实模块可以处理构造输入；
    
- 人工测试用于发现自动测试没有覆盖的交互问题。
    

普通 pytest 默认不调用真实 API，真实测试需要：

```
RUN_REAL_LLM_TESTS=1
```

### 实际结果

项目形成 270 个以上自动测试、真实模型场景、人工测试计划、Context 基线和终端录屏脚本。

## 15. 为什么不用 Playwright 操作 PowerShell 录屏

### 问题

希望根据测试文档自动完成终端演示，但 Playwright 主要用于浏览器自动化，直接控制 PowerShell 并不稳定。

### Prompt

提示词：第八轮次

### AI 建议

为 CLI 增加：

```
--script
--step-delay
```

脚本中每行一个用户输入，CLI 按顺序调用真实 AgentRuntime。

### 我的判断

我选择直接扩展 CLI，而不是使用：

- Playwright；
    
- PyAutoGUI；
    
- 坐标点击；
    
- 外部键盘模拟。
    

这种方式使用的仍是：

- 真实 CLI；
    
- 真实 qwen API；
    
- 真实 AgentRuntime；
    
- 真实工具；
    
- 真实 Trace。
    

同时演示内容可重复，适合终端录屏。

### 实际结果

完成 `scenarios/recording-demo.txt` 和 CLI 脚本模式，可按固定节奏演示核心能力。

## 16. 最终范围控制

### 问题

随着测试深入，可以继续增加真实网络搜索、向量数据库、RAG、多 Agent、MCP、Web UI 和完整登录系统，但会偏离“最小可用 Agent”题目。

### AI 建议

部分能力可以作为后续扩展，但不属于当前笔试必要范围。

### 我的判断

我最终冻结以下边界：

- search 保持 Mock；
    
- 本地文档使用关键词搜索，不实现向量 RAG；
    
- user_id 是逻辑隔离键，不实现密码认证；
    
- SQLite 用于最小持久化；
    
- 不实现多 Agent；
    
- 不实现 MCP；
    
- 不实现 Web UI；
    
- 不实现分布式锁；
    
- 不声称读取模型完整思维链。
    

项目重点保持在：

```
自研 Agent Runtime
真实 Function Calling
工具注册
多步 Loop
Session 隔离
Context 管理
异常处理
Trace
测试
```

### 实际结果

项目功能范围与题目保持一致，没有因为继续堆叠技术而失去“最小可用”定位。
